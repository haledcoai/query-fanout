On 2026-10-08 the user asked for SerpApi inside the Query Fan-Out Generator page (https://claude.ai/artifact/RsdqCpsMdV6uUsgnXw7EVU). Artifact pages have no network access, so the page's main "Phân tích" button (since 2026-10-08 the user required the full run as the default, not a separate button) calls the Claude Code Remote connector `fire_trigger` on routine trig_01GwvKbnDm7jnovRY7rie5dq with text JSON {root, count, job, otterly?}. The page also got a "Làm mới" reset button the same day.

When fired from the page, the platform starts a FRESH cloud session (origin force_run_trigger), not the thread that created the routine. That session has no /mnt/project-files, so it cannot read the SerpApi key file. Network secrets do not work for SerpApi: they only inject headers, and SerpApi returned 401 for an Authorization Bearer header (tested 2026-10-08); it needs the api_key query parameter. So the key is set via `echo 'KEY' > ~/.serpapi-key` in the environment's Setup script; confirmed working 2026-10-08 (page run for "đèn pha năng lượng mặt trời" got Google data). The routine reads SERPAPI_API_KEY env var, then ~/.serpapi-key, then the project file. The routine writes results to db collection "runs", doc_id = job, source "nut-trang", and must not post to project chat (an early version did).

**Why:** the user uses the page internally and wants Google data from a button, not only from /query-fan-out in chat.

**How to apply:** if a button run lacks Google data, first check that the Setup script still writes ~/.serpapi-key. A full page run takes about 5 minutes (fresh session, 5 web-search agents, SerpApi). The page passes count (ceiling, same as skill) and lang to the routine. If the full run cannot start (not owner, no connector consent), the page falls back to the quick Claude-only analysis and says why. Related: [[query-fan-out-skill-version]].

Otterly on page runs (2026-10-08): the user only uses the page and wants Otterly queries included. Auto-submitting to Otterly from the routine was tried on 2026-10-08 and REVERTED: the fresh session's safety checks blocked sending the email form, and in that same run also blocked reading the SerpApi key, so the run lost all Google data (doc nut-muzb7xim). The routine now forbids POSTs to outside services and states the key is the owner's own, for this use. The user submits on geo.otterly.ai themselves. Otterly results come only by email (link ?result=ID), and page sessions have no Gmail. So the page shows a "Thêm Otterly" box on a result without Otterly data. Pasting the email link fires the routine with {mode:"otterly", job, root, otterly_url}. The routine fetches modes aimode/aio/chatgpt, filters per Bước 0b, merges into runs/<job>, and sets otterly_cap_nhat (or loi_otterly on failure). The user said the extras (nhận xét, trích dẫn, Otterly-dropped list, row order) are not important to them; the priority is a complete query list including Otterly.

Two devices (2026-10-08, user asked for both): page runs call google and google_ai_mode with device=desktop and device=mobile, autocomplete once (SerpApi drops device for autocomplete). Test on "đèn pha năng lượng mặt trời": mobile Related searches were completely different (12 vs 8, none shared), AI Mode headings and citations differed, AI Overview and Autocomplete were identical. Cost is about 5 searches per root (6-7 with page_token calls). On 2026-10-09 the user saved the two-device skill; verified identical to /mnt/project-files/query-fan-out/SKILL.md, so page and skill are in sync.
